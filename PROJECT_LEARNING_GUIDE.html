Section 02

Problem & Solution

The Problem

Businesses store data in two separate places that don't talk to each other:

  • Structured data — in relational databases (like PostgreSQL): orders, users, products, revenue
  • Unstructured data — in documents (PDF, DOCX, TXT): policies, rules, guides, contracts

To get answers, someone must:

  1. Know SQL to write database queries
  2. Manually read and search through documents
  3. Combine both sources in their head

This creates a knowledge barrier — only technical people can get insights from the system.

My Solution

A single chat interface backed by a multi-agent AI system that:

  1. Accepts any question in plain English
  2. Automatically decides if the question is about the database, a document, or both
  3. Routes the question to the right specialist agent
  4. Returns a clear, formatted answer — sometimes as a table or chart

No SQL required. No document searching. The AI handles everything.

The E-Commerce Context

The system is pre-loaded with a PostgreSQL database containing:

  • 100 users with addresses
  • 10 product categories, 50 products
  • Orders, payments, shipments, reviews (2,530+ records total)
  • 11 tables connected by foreign keys

This simulates a real business database that a manager, analyst, or customer support agent would need to query.

Section 05

Technologies Deep Dive

🐍 Python 3.14 + uv

What it is: Python is the programming language. uv is an extremely fast package manager (alternative to pip).

Why I used it: Python has the richest AI/ML library ecosystem. uv installs dependencies ~10× faster than pip and manages virtual environments automatically.

# Run backend without manually activating virtualenv
uv run mcp-server

⚡ FastAPI

What it is: A modern Python web framework for building REST APIs.

Why I used it: FastAPI is async-native (important for LangGraph's async agents), generates automatic API docs, and uses Python type hints for validation.

Key endpoints in server.py:

EndpointMethodPurpose
/api/healthGETCheck if backend + MCP are ready
/api/documentsGETList uploaded documents
/api/uploadPOSTUpload a document, rebuild FAISS index
/api/chatPOSTSend a question, get AI answer

🕸️ LangGraph + LangChain

What it is: LangGraph builds stateful agent workflows as graphs. LangChain provides the building blocks (tools, models, prompts).

Why I used it: create_react_agent from LangGraph implements the ReAct pattern — Reason + Act — where the agent decides which tool to call, calls it, reads the result, and decides again until it has a final answer.

Pattern used: All 5 agents (supervisor + 4 specialists) are built with create_react_agent.

🔌 MCP (Model Context Protocol)

What it is: A protocol that exposes external tools (like a database) to AI models in a standardized way.

Why I used it: Instead of writing raw SQL queries manually, MCP provides tools the AI can call directly. mcp-postgres-server (via npx) translates those tool calls into real PostgreSQL queries.

Tools MCP exposes: list_schemas, list_tables, describe_table, query

How it's connected in postgres_client.py:

MultiServerMCPClient({
  "postgres": {
    "command": "npx",
    "args": ["-y", "mcp-postgres-server"],
    "transport": "stdio",  # communicates via stdin/stdout
    "env": {"DATABASE_URL": ..., "PG_ALLOW_WRITE": "false"}
  }
})

🤖 Groq LLM

What it is: Groq is a cloud AI provider offering fast LLM inference.

Why I used it: Groq's API is fast (low latency) and free-tier friendly. The model openai/gpt-oss-120b handles complex multi-step reasoning for agent routing.

🗃️ FAISS + HuggingFace Embeddings (RAG)

What FAISS is: Facebook's library for fast similarity search over vectors.

What embeddings are: Numbers (vectors) that represent the meaning of text. Similar text has similar numbers, allowing "semantic" search.

The model: sentence-transformers/all-MiniLM-L6-v2 — a small, fast model that runs on CPU. Free, no API key needed.

Why local FAISS: No external service needed. The index is saved to .faiss_index/ on disk and loaded on startup.

⚛️ React 18 + Vite + TypeScript

React: JavaScript library for building interactive UIs with components.

Vite: Fast build tool that proxies /api calls to the backend during development — no CORS issues.

TypeScript: Adds types to JavaScript, catching bugs at compile time.

📊 Recharts + Chart Detection

Recharts: A React chart library supporting Bar, Line, Area, and Pie charts.

Chart detection (chartDetector.ts): Parses markdown tables from AI responses. If the table has numeric columns, it recommends a chart type (Bar for categories, Pie for distributions, Line for time-series) and renders it automatically.

Section 06

Actual Workflows

Workflow 1 — Document Upload + Indexing

1

User uploads a file via the React sidebar

Frontend calls POST /api/upload with the file as FormData

2

FastAPI receives the file (server.py → upload_document())

Saves it to rag/documents/. If it's a .docx, extracts text using python-docx and saves a companion .txt file so the existing loader can read it.

3

Calls rebuild_supervisor()

This triggers the full RAG rebuild: load → chunk → embed → index → save

4

Document loading (loader.py → load_documents())

Scans rag/documents/. Loads .pdf with PyPDFLoader; .txt and .md with TextLoader.

5

Text splitting (retriever.py → get_retriever(rebuild=True))

Uses RecursiveCharacterTextSplitter with chunk_size=500, chunk_overlap=100. Splits documents into overlapping text chunks for better retrieval.

6

Embedding generation (embeddings.py → get_embeddings())

Converts each chunk to a 384-dimensional vector using all-MiniLM-L6-v2 on CPU.

7

FAISS indexing (vectorstore.py → create_vectorstore())

Builds a FAISS index from all chunk embeddings. Saves it to .faiss_index/ (index.faiss + index.pkl).

8

Supervisor rebuilt with fresh RAG tool

All future questions can now retrieve content from the new document.

Workflow 2 — Database Query via MCP

1

User types: "Who are the top 5 customers by spending?"

Frontend calls POST /api/chat with the message and conversation history

2

Supervisor Agent receives the question

Decides this is a data retrieval question → calls tool ask_query_agent

3

Query Agent (database_agent.py) is invoked

It has access only to the query MCP tool. It formulates SQL: SELECT u.first_name, u.last_name, u.email, SUM(o.total_amount)... ORDER BY total DESC LIMIT 5

4

MCP tool query executes the SQL

The mcp-postgres-server (running as a subprocess via npx stdio) runs the SQL against the real PostgreSQL database and returns the result rows as JSON.

5

Query Agent formats the response

Returns a markdown table of the top 5 customers with names, emails, and spending totals.

6

Supervisor returns the final answer to FastAPI

FastAPI returns it in the ChatResponse JSON.

7

Frontend renders the table + chart

chartDetector.ts → detectVisualData() parses the markdown table, finds numeric "spending" column, recommends a Bar chart. DynamicChart.tsx renders it with Recharts.

Workflow 3 — Document RAG Query

1

User asks: "What is the return policy?"

Supervisor decides this is a document question → calls ask_rag_agent

2

RAG Agent is invoked (rag_agent.py)

It calls search_knowledge_base(question)

3

FAISS similarity search

The question is embedded to a vector. FAISS finds the top-4 most similar document chunks (k=4) using cosine similarity.

4

Retrieved chunks are returned with source file names

Format: Source: return_policy.txt\nContent: ...

5

RAG Agent synthesizes an answer

Uses the retrieved content to write a clear answer, citing the source document.

Workflow 4 — LLM Answer Generation

Every agent in this system uses the same Groq LLM (ChatGroq) with different prompts and tools:

  • The LLM reads the question and its available tools
  • It decides which tool to call and with what argument
  • It calls the tool, reads the result
  • It decides again — call another tool, or write the final answer
  • This loop is the ReAct (Reason + Act) pattern

The Groq API receives each message, processes it on specialized LLM hardware (LPUs), and returns the response extremely fast — typically under 2 seconds per step.

Code Walkthrough

🔧 Backend startup — server.py → lifespan()

When the FastAPI backend starts, the lifespan async context manager runs in this order:

1. ChatGroq(model="openai/gpt-oss-120b")       # Create LLM
2. await get_postgres_tools()               # Start MCP subprocess
3. build_database_agents(llm, mcp_tools)    # 3 DB agents + tool wrappers
4. build_rag_agent(llm, rebuild=False)      # Load FAISS or build if missing
5. build_supervisor(llm, all_agent_tools)   # Supervisor with 4 tools

Everything is stored in app_state dict so it persists across requests without reinitializing.

🔌 MCP Connection — postgres_client.py → create_mcp_client()

MultiServerMCPClient spawns npx -y mcp-postgres-server as a subprocess and communicates with it over stdin/stdout (stdio transport). The server exposes PostgreSQL as AI-callable tools. PG_ALLOW_WRITE=false ensures only read-only SQL is permitted.

🤖 Specialist Agents — database_agent.py → build_database_agents()

Three agents are created with create_react_agent, each with a subset of MCP tools and a specific prompt:

Agent variableMCP tools givenExposed as tool
schema_agentlist_schemas, list_tables, describe_tableask_schema_agent
query_agentqueryask_query_agent
analytics_agentquery, list_tables, describe_tableask_analytics_agent

Each specialist is wrapped with @tool so the supervisor can call it like any other tool.

📄 RAG Agent — rag_agent.py → build_rag_agent()

Calls get_retriever(rebuild) to get a FAISS retriever. Creates a search_knowledge_base tool that:

  1. Calls retriever.invoke(question) → gets top-4 chunks
  2. Returns each chunk's content + source file name

Wraps a rag_agent (ReAct) around it, then wraps that in an outer ask_rag_agent tool for the supervisor.

🗃️ FAISS Pipeline — retriever.py → get_retriever()

if rebuild:
    documents = load_documents()           # loader.py: PDF+TXT+MD
    chunks = RecursiveCharacterTextSplitter(
        chunk_size=500, chunk_overlap=100
    ).split_documents(documents)
    vectorstore = create_vectorstore(chunks, embeddings)  # saves to .faiss_index/
else:
    vectorstore = load_vectorstore(embeddings)    # loads from .faiss_index/

retriever = vectorstore.as_retriever(search_kwargs={"k": 4})

📊 Chart Detection — chartDetector.ts → detectVisualData()

When an AI message arrives, detectVisualData(markdown) runs:

  1. Scans lines for pipe-delimited markdown table patterns
  2. Validates the separator row (e.g. --- | :---: | ---)
  3. Checks each column: if >70% of rows are numeric → it's a data column
  4. Non-numeric first column → category axis
  5. Recommends: Pie if 2–8 rows with "status/category/distribution" in header; Line if time-based; Bar otherwise

Returns a DetectedVisual object used by ChatMessage.tsx to render DynamicChart.tsx.

🌐 API Service — services/api.ts

Four exported async functions:

  • checkHealth() — GET /api/health
  • fetchDocuments() — GET /api/documents
  • uploadDocument(file) — POST /api/upload (multipart)
  • sendChatMessage(message, history) — POST /api/chat; passes last 8 messages as history for follow-up context

All use VITE_API_URL as base URL (defaults to empty string; Vite proxy handles /api → localhost:8001 in dev).

Section 09

What I Learned

🤖 AI Agents ≠ just chatbots

Agents have tools they can call in a loop — reason, act, observe, repeat — until they reach a goal. This is fundamentally different from a simple prompt-response chat.

🔌 MCP standardizes AI tool use

Instead of writing custom database connectors for each AI, MCP provides a standard protocol. Any AI that understands MCP can query any MCP-compatible database.

📐 RAG fills LLM knowledge gaps

LLMs don't know about your specific business documents. RAG retrieves relevant document chunks and feeds them as context — grounding the AI in your actual data.

⚡ Async is essential for multi-agent systems

When multiple agents invoke each other, async/await ensures the system doesn't block. Python's asyncio + FastAPI's async endpoints make this manageable.

🗂️ Separation of concerns

Each specialist agent has one job and one set of tools. This makes the system easier to debug, test, and extend — adding a new agent doesn't break others.

📊 Frontend can be smart about data

Instead of hardcoding chart types, chartDetector.ts analyzes the AI's markdown output dynamically. The frontend adapts to whatever data the AI returns.

Challenges I solved

  • FAISS index path resolution — Used Path(__file__).resolve().parents[3] to reliably find the index directory regardless of where the script is run from
  • DOCX support in RAG — The document loader only handles PDF/TXT/MD. DOCX files are converted to .txt on upload using python-docx, without changing the loader logic
  • Port conflicts — Added PORT env variable so the backend port is configurable
  • CORS in development — Vite's proxy handles /api calls during development, eliminating browser CORS issues without changing backend CORS settings
  • MCP subprocess lifecycle — The MCP server runs as a subprocess; the client must be initialized before any agent tools can be called, which is why it's in the FastAPI lifespan

Technical Q&A

What is MCP and why did you use it?
MCP (Model Context Protocol) is a standard for exposing external tools — like a database — to AI models. I used mcp-postgres-server via npx which runs as a subprocess and communicates over stdio. It exposes PostgreSQL as callable tools: list_schemas, list_tables, describe_table, and query. The LangChain MCP adapter bridges these tools into LangChain-compatible format, so agents can call them naturally.
What is RAG and how did you implement it?
RAG stands for Retrieval-Augmented Generation. Instead of asking the LLM to answer from memory, I retrieve relevant text chunks from documents first, then pass them as context to the LLM. I implemented it using: (1) document loading with PyPDFLoader and TextLoader, (2) chunking with RecursiveCharacterTextSplitter (500 chars, 100 overlap), (3) embedding with HuggingFace all-MiniLM-L6-v2, (4) FAISS for vector storage and similarity search (top-4 chunks), and (5) the retrieved content fed to the RAG agent as context.
What is LangGraph and how did you use it?
LangGraph is a library for building stateful, multi-step AI agent workflows. I used its create_react_agent function to build all 5 agents: 3 database agents, 1 RAG agent, and 1 supervisor. Each agent follows the ReAct pattern — it reasons about what tool to call, calls it, reads the result, and decides its next step. The supervisor agent gets the 4 specialist agents as its tools, allowing hierarchical delegation.
How does the supervisor know which agent to call?
The supervisor is a ReAct agent with a routing prompt that describes what each specialist does. The LLM reads the user's question and the tool descriptions, then decides which tool(s) to call. This is a form of "tool-calling" LLM behavior — no hardcoded if/else routing. The LLM reasons about the question type and delegates accordingly.
Why FAISS instead of a vector database like Pinecone?
FAISS is a local, file-based vector index — no external service, no API key, no cost. For an MVP with moderate document volume, it's simpler and faster to set up. The tradeoff is that it doesn't scale to millions of documents and can't be queried from multiple servers simultaneously. For production, I'd migrate to pgvector (PostgreSQL extension) or a managed service like Pinecone.
How does the frontend detect when to show a chart?
When an AI message arrives, detectVisualData() in chartDetector.ts scans the markdown for pipe-delimited table syntax. If it finds a valid table with at least 2 data rows, it checks each column: if more than 70% of values are numeric, it's a data column. The first non-numeric column is the category axis. Chart type is chosen by heuristics: Pie for small distributions (2-8 rows with "status/category" in the header), Line for time-based categories, Bar for everything else.
What would you change to make this production-ready?
I would: (1) add authentication (JWT tokens, user sessions), (2) replace FAISS with pgvector to store embeddings in the same PostgreSQL database, (3) add streaming responses so the UI shows output word by word, (4) add request rate limiting and error monitoring, (5) containerize with Docker Compose, and (6) add persistent conversation history stored in a database table.
Explain how a user question flows through the whole system.
User types a question → React frontend calls POST /api/chat → FastAPI passes it to the supervisor agent (LangGraph) → supervisor LLM decides which specialist agent tool to call → specialist agent calls MCP tools (for DB) or searches FAISS (for docs) → specialist returns structured text to supervisor → supervisor synthesizes a final answer → FastAPI returns it as JSON → React renders it as markdown, optionally as a table + chart.
